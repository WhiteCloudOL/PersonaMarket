# 排行榜口径与维护

排行榜使用当前审核通过的公开作品，按全平台、MaiBot 或 AstrBot 分别计算。导出统计的定义与去重见 [公开统计与导出口径](METRICS.md)

| 榜单     | 时间范围           | 排序依据                                                |
| -------- | ------------------ | ------------------------------------------------------- |
| 热门     | 过去 7×24 小时     | 有效点赞 ×3、收藏 ×4、导出 ×1，分别按事件年龄衰减后求和 |
| 点赞     | 7 天、30 天、全部  | 窗口内首次添加且仍有效的去重点赞；总榜统计当前有效关系  |
| 收藏     | 7 天、30 天、全部  | 窗口内首次添加且仍有效的去重收藏；总榜统计当前有效关系  |
| 下载     | 7 天、30 天、全部  | 作品的去重有效导出数，排除作者本人                      |
| 新作     | 运营窗口或固定30天 | 作品首次公开时间，补丁发布保留原首次时间                |
| 最近更新 | 全部               | 当前公开版本的发布时间                                  |

可配置算法为 `interactions-v2`，默认热门权重为点赞3、收藏4、导出1，每项事实的分数为 `权重 × 0.5^(事件年龄秒数 / 604800)`，7 天半衰期让近期互动更有分量。热门、点赞和收藏的时间窗口按滚动 24 小时计算；下载时间窗口保留 UTC 日期口径，包含今天及此前 6 或 29 天。同分按首次公开时间、作品 ID 稳定排列

管理员在「网站设置 → 排行与运营」调整权重、刷新周期、展示上限和新作窗口。权重可为0–100的有限小数，均为0时热门榜为空，独立的点赞、收藏和下载榜继续计算。刷新周期为1–60分钟，每榜展示1–1000项，运营新作窗口为1–365天；默认5分钟、1000项、30天。去重、邮箱资格、读取时公开检查和7天半衰期不受这些参数影响

每次保存配置在同一事务内记录前后差异、内部修订及新计算请求。只有新批次成功后才替换公开结果，管理页显示最近请求和实际成功批次；保存成功不能代替计算成功。新请求冻结完整设置和修订，排队期间修改配置不会改变已接受任务。历史 `interactions-v1` 保留固定3/4/1，探索页即时热度也继续使用此固定口径；排行和探索可以因此有不同分数

排行关系来自正常且邮箱已验证的账号，排除作者本人、已取消和未来时间的关系。取消后再次添加保留原首次时间，不会刷新成新增互动；已有历史关系按其原首次时间参与回建。卡片的点赞和收藏总数保留当前有效关系总量，可能包含本人互动，因此可与排行有效数量不同；收藏者身份保持私有

旧版 `exports-v1` 热门仅统计衰减后的有效导出，原下载、新作和更新规则继续保留。旧快照会明确显示版本标记，不能将旧分数解释成新版互动热度；点赞和收藏榜需要新版快照

有效导出表示服务端已准备并提供文件响应，同一主体、同一作品在同一 UTC 日期内跨版本、跨格式最多计一次。它并不证明用户已完成保存或安装；匿名主体的防刷去重存在近似性

## 快照与公开读取

独立 Worker 按冻结刷新周期安排计算，维护检查约每分钟执行一次，队列繁忙时可能延迟。`interactions-v2` 包含39个榜单、窗口与平台组合，`interactions-v1` 保留36个，`exports-v1` 保留18个。每个组合取本批展示上限及额外一项判断截断，整批使用同一计算时刻，在同一事务内提交全部排序事实与完成状态；计算失败时继续读取上一批成功结果，并按该批原周期标注过期状态

排序分数和有效数量在批次生成时固定，新增、取消和参与账号状态变化在下一批计算中体现。默认优先读取新版成功快照，新版尚未就绪时，已有榜单可以继续读取旧版；点赞和收藏榜会给出准备或重试状态，不以空成功响应代替缺失快照

快照保存 ID 和排序事实，公开卡片仍从当前获批内容读取。隐藏、下架或失去当前公开版本资格的条目会在每次读取时过滤，不能通过旧快照地址继续访问。新公开版本替换旧指针后，下一批刷新会使用新版本

每种算法最近12批成功快照用于分页。默认读取优先采用新算法及更高设置修订，迟到的旧算法或旧修订不替换新修订成功批次。接口返回 `snapshotId`，后续页应携带它以保持同一批排序；该批过期后返回明确错误，刷新排行榜即可重新开始。公开资格变化仍会即时影响同一批的可见结果与页码

新作运营窗口使用明确的 `window=newcomer`，响应的 `windowDays` 和冻结定义标明实际天数。显式 `window=30d` 以及旧页面省略window的新作分享地址继续表示30天，不被今日配置重解释；旧算法快照不包含运营窗口。页面点击「新作」会选运营窗口，固定「近30天」仍可切换

公开接口为 `GET /api/v1/rankings`，参数由 [OpenAPI 契约](openapi.json) 定义。`kind` 可选 `hot`、`likes`、`favorites`、`downloads`、`new`、`updated`，`window` 仅接受上表对应范围；响应包含实际算法版本，每页最多 20 项，最多 50 页。页面的「统计说明」可展开查看完整口径

## 受控重建与升级

在已配置项目运行环境的宿主机执行：

```sh
pnpm rankings:rebuild
```

命令按当前设置提交带事务 Outbox 的新请求并返回生成批次 ID，实际计算由 Worker 完成。保持 PostgreSQL、Redis 与 Worker 健康，检查 Worker 日志中的批次任务结果；失败任务有限次重试并保留失败记录，排查原因后可以再次提交重建请求。这是创建新批次，不等同于原失败请求已恢复；重建使用执行时有效业务事实，不能精确还原任意历史时刻

需要恢复某个原失败批次时，使用管理后台「失败任务」中的榜单生成详情。系统保留原批次ID、算法与冻结定义，先确认本轮已经终结失败，再创建受控事件；上限三轮，间隔60秒。原事件与人工记录可以核对，旧轮迟到不会覆盖新轮；成功须同时具备本算法完整榜板与业务消费回执。详见[失败任务](ADMIN_TASKS.md)。

互动榜单升级包含 `0040_interaction_rankings`；可配置批次使用 `0045_ranking_settings`，增加冻结定义、修订与身份约束，默认配置仅在不存在时插入，已有配置不被覆盖。先按 [部署说明](DEPLOYMENT.md) 停写与备份，迁移成功后再启动匹配的新 API 和 Worker；新 Worker 按请求保存的实际版本处理原有旧版排队任务

回退使用匹配版本与受控备份，避免旧 Worker 接收新版算法任务；不通过删除关系、原始事件或日汇总来重建榜单，不改写已执行迁移
