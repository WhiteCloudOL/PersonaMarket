# 维护与系统设置

管理员在「站点设置 → 维护与系统」管理维护开关与公共提示。默认关闭维护，提示为空；提示最多500个Unicode字符，按纯文本显示，不执行HTML或Markdown。关闭维护会保留已保存提示，网站只在维护开启时显示这条公共提醒。维护提示独立于既有公告。

读取设置、变更记录和API运行信息只需有效管理员会话。保存属于高危操作，需要十分钟内的身份确认；未绑定MFA时使用当前密码，已绑定时使用身份验证器或恢复码。身份确认保留原表单，由管理员再次保存，不自动重发原请求。

## 维护期间的行为

| 能力                                                                | 维护期间                                                             |
| ------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 公开页面、审核通过的历史版本、本人私有内容读取                      | 沿原权限继续                                                         |
| 新注册、创作保存、导入、上传、新远程图片任务                        | 暂时拒绝新业务提交                                                   |
| 作者Release送审、撤回、恢复、公开状态及公开版切换                   | 暂时拒绝；管理员通过创作者入口同样适用                               |
| 点赞/收藏增加或移除、评论、资料草稿/送审/撤回、举报、通知偏好与已读 | 暂时拒绝新业务提交                                                   |
| 实际GET下载和导出                                                   | 在发送文件前拒绝，不增加下载统计或匿名下载标识                       |
| 导出预览、HEAD文件头探测                                            | 沿原权限只读；文件头探测不计作下载                                   |
| 登录、退出、会话撤销、密码/邮箱/MFA安全与必要恢复                   | 沿原身份、权限、限流及近期验证规则继续，不强退正常会话               |
| 专用管理审核、运营、规则及设置                                      | 沿原角色资格继续，包括已有权限的审核员；高危处置仍要求原近期身份确认 |
| 已排队Worker、Outbox、必要补偿和引用安全回收                        | 沿原幂等、权限与引用保护继续                                         |

维护错误为`MAINTENANCE_MODE`，HTTP503，并带`Retry-After: 60`。60秒表示稍后检查的建议间隔，不保证站点将在60秒后恢复。输入、草稿候选、原因和原请求标识应保留，维护关闭后明确重试。网络结果未知时先用原始候选、修订和幂等键核对，不换键盲目重发。

维护只控制新普通请求的最终业务提交。已经取得普通共享门禁的事务先完成，开启维护的保存会等待该事务结束；开启成功后，新的普通最终事务读到开启状态就拒绝。超时或并发冲突会明确失败，不能当成已开启。

这不是数据库或磁盘的全局停写：管理、安全、后台任务和必要补偿仍会写入；在途解码或文件暂存也可能产生随后清理的临时字节。需要一致性备份时，仍须按[数据维护](OPERATIONS.md)明确暂停/排空相关Web、API和Worker写入，不能只打开维护开关。

## 保存与只读历史

读取返回`ETag: "system-修订号"`。保存完整`{data,confirmed:true}`，携带CSRF、当前`If-Match`与UUID `Idempotency-Key`；新界面同时发送`X-Expected-Account`核对实际账号。该核对头不授予管理员权限。

设置、修订、差异历史、安全审计和幂等结果在同一事务提交。旧修订返回`REVISION_CONFLICT`，应读取最新值、保留自己的输入并再次确认；同键异请求返回冲突。成功同键请求可在有效管理员会话内只读核对，不重复提交，也不因原近期验证过期而要求重做已成功的副作用。核对返回当前设置，后续管理员更新应结合历史区分。

变更记录每页20条，页码1–100，按修订倒序，只能管理员读取。设置页记录展示前后设置、修改者与时间；没有直接修改历史或回滚审计的入口。

## API与运行信息

以下路径均以`/api/v1`为前缀：

| 方法与路径                                  | operationId                |
| ------------------------------------------- | -------------------------- |
| `GET /public/system-status`                 | `getPublicSystemStatus`    |
| `GET /admin/settings/system`                | `getSystemSettings`        |
| `PATCH /admin/settings/system`              | `updateSystemSettings`     |
| `GET /admin/settings/system/records?page=1` | `getSystemSettingsRecords` |
| `GET /admin/settings/system/runtime`        | `getSystemRuntime`         |

公开状态为no-store白名单，只包含维护开关、公共提示和设置修订；不公开私有理由、历史、用户统计、邮件连接或环境秘密。配置缺失或非法时，公开状态和普通最终写入明确503，不把未知解释成维护关闭。此时认证上下文只把注册可用性置为false，仍提供真实身份与CSRF，保留管理员登录、MFA和必要账号安全恢复。独立配置错误的降级不吞掉其他数据库或身份错误。

运行信息只说明API自身产物和实际Node版本，属于只读字段。源码修订、脏树标记、构建时间来自构建时固化的元数据，在API进程启动时读取为该进程的快照；原地重新构建不会将旧进程标成新版本，新产物须启动新进程。缺少有效产物信息显示未知，不用运行时工作区HEAD、镜像标签或人工输入替代。API版本不能证明Web和Worker同版。

本机通过`pnpm build`或其他根目录构建入口生成API产物，容器通过`node scripts/build-images.mjs api`等明确服务入口固化来源。API的`dist/build-info.json`随构建产物交付；构建缓存包含来源输入和记录脚本，缓存命中保留原时间。直接运行Compose构建但未提供受控来源时，缺少Git的构建上下文显示未知，不能将人工镜像标签当成源码证明。

依赖就绪复用`/health/ready`现有PG/Redis检查，不表示SMTP或外部邮件最终送达；Storage和队列观察沿用管理概览的采样时间与ready/partial/unavailable口径。任务失败继续从已有任务管理页核对，不用新造的零值或成功标签代替实际观察。

Docker组合由Caddy将`/health/*`送往API。独立Web的固定`GET /health/ready`转接在请求时读取服务端`API_INTERNAL_ORIGIN`，只访问API同名路径，不接收目标URL、查询或来访凭据；真实上游200且通过共享健康契约才返回成功。转接不缓存，失败返回安全503及本次Web请求标识，不沿用旧成功，也不暴露内部响应正文。它不增加新的业务写入或运行环境设置入口。

## 升级和维护

`0049_system_settings.sql`在49条迁移基础上补到50条，仅在缺少`system`行时插入默认关闭配置；保留所有既有设置、修订、时间、账号和其他业务数据。已有System值原样保留，非法既存值不会被静默修复或以默认值覆盖。旧已执行迁移保持不变；0049首次成功执行后同样冻结。

按既有受控流程备份、单一进程迁移并部署匹配的API/Web/生成客户端，升级后刷新旧页面。缺失或非法配置应先核对升级与配置来源，通过受控维护流程恢复；不删除迁移记录、不修改已执行SQL，也不在本说明中提供绕过权限的特殊请求头。

专项测试入口为`tests/unit/system-settings.test.ts`、`tests/integration/system-settings.test.ts`、`system-settings-upgrade.test.ts`、`system-maintenance-auth-exports.test.ts`，以及创作/素材与社区维护专项。它们使用隔离自有数据和正常PG/Redis/Mailpit业务流程，不停止基础设施或注入不可达服务。测试源码存在不代表验收通过，实际命令、退出码与覆盖以本轮执行记录为准。
