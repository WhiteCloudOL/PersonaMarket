# 邮件投递

账号验证、安全提醒和审核邮件通过事务 Outbox 交付给 Worker。投递内容保持加密，数据库中的 `mail_deliveries` 只记录事件标识、密文摘要、状态、处理尝试和安全错误码，不复制收件地址、正文或验证令牌。

SMTP 返回接收成功后，投递状态和消费回执在同一个数据库事务提交。`sent` 表示 SMTP 已确认接收，不代表对方邮箱已完成送达；外部提供方的退信、拦截和收件箱结果仍需另外核对。稳定的 Message-ID 也不能代替发送端的重复保护。

| 状态        | 含义                                       | 处理方式                                         |
| ----------- | ------------------------------------------ | ------------------------------------------------ |
| `sending`   | 处理权已持久登记，发送阶段尚未完成         | 等待当前 Worker；前一会话中断后不推定邮件未发送  |
| `sent`      | SMTP 接收及数据库回执已确认                | 同一事件再次交付时直接识别为已处理               |
| `failed`    | 已有证据确认未完成发送，例如发送前缺少配置 | 保留最多五次处理尝试，耗尽后先核对配置和业务状态 |
| `uncertain` | SMTP 应答丢失、中断，或接收后回执无法确认  | 停止自动重发，先核对提供方记录和原业务状态       |

处理尝试分别记录在数据库中，不能使用新的队列任务标识重置。同一事件的并发处理受数据库锁保护；未知结果和已送达终态不能改回待发送，也不能直接修改已经启动事件的邮件内容。

网络错误不能仅凭 `CONN` 判断为未发送：连接也可能在发送正文后断开。只有明确的发送前失败或 SMTP 拒绝证据才允许继续有限尝试。遇到 `uncertain` 时，不要直接重放队列中的密文或验证链接；如链接过期，应通过对应的账号验证、找回或其他业务入口重新发起。

新投递保护不自动回填旧邮件的确定状态。历史已处理回执继续有效，没有记录不能解释为“尚未发送”或“发送零次”。

升级会追加 `0041_mail_delivery_guard`，不改写旧迁移、旧邮件密文或管理员配置。按[数据维护](OPERATIONS.md)先备份并暂停写入，使用受控迁移进程升级，再启动匹配版本的 API 和 Worker；保留备份和旧镜像以便评估回退。投递记录属于业务数据库，备份恢复时与 Outbox、消费回执及加密配置一起保留。
